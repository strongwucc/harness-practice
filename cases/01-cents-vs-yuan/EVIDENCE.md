# 证据分级：历史证据 vs 合成演示

本案例混合了两类内容。为避免把合成演示误当成历史证据（那会重演本案例批判的「假绿」错误），逐项分级如下。

## A. 历史证据（私有仓库内可由持有权限者核查；本表为脱敏陈述，公开读者无法直接核查原始记录）

| # | 证据 | 形态 | 可核验性 |
|---|------|------|---------|
| A1 | 事故条目：提交订单必拒 price_changed——渠道 item_price 分元单位错位 | evals/ 结构化回归条目（日期/根因/复现/期望四段） | 私有仓库 evals 文件（本文档引用其脱敏版） |
| A2 | 修复提交：响应侧比较修复 + 金额归一化函数新增 + 4 个测试文件 mock 改分 + 新增 Formatter 单测 + evals 条目当场固化 | 私有仓库修复提交，9 文件 +92/-29，提交声明含 Claude 共同署名 | commit 元数据（私有仓库内可查，公开版不携带哈希） |
| A3 | 「mock 按 spec 验参，防同源假绿」约束书面化（早于本事故 3 天） | 私有设计文档的测试章节 | 文档日期与内容 |
| A4 | 同族契约失真：事故当天 4 个「真机契约校准」修复（响应键位/幂等键/轮询契约） | 同日 commit 序列 | commit 元数据 |
| A5 | 反馈到修复提交相隔 22 分钟 | commit 时间戳与反馈记录时间 | 时间戳 |

## B. 合成演示（本仓库代码，为公开复现构造）

| # | 内容 | 与历史的关系 |
|---|------|------------|
| B1 | `contract.py` 契约模拟层 | 对契约**结构**的抽象（按分回传/按元记账），非任何真实渠道报文 |
| B2 | `reconciliation/broken.py` / `fixed.py` | 事故机制级的简化重建；原事故为 PHP/Laravel 栈（bccomp 比较），重建以 Python 表达同一机制 |
| B3 | 两份测试文件 | 「事故前 mock 组」与「修复后 fixture 组」的形态重建，非原测试文件拷贝 |

## C. 明确不做声称的事项

- 不声称修复过程只用了 22 分钟——22 分钟是「反馈记录到修复提交」的时间差，过程中是否存在未记录的排查工作不可知
- 不声称人工与 Agent 的具体分工——提交署名只证明参与声明，定位根因/制定方案/逐处修改的归属无法从 commit 链还原
- 不声称该案例证明了「整数分设计」的普遍有效性——本事故直接支持的是「跨边界单位必须显式归一后比较」；作品采用整数分是相关但独立的设计选择
- 不声称「事故驱动了后来的守卫体系」——事故与后续守卫设计存在时间关联，因果驱动关系无独立证据，不写入本案例
