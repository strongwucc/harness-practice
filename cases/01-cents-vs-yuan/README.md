# 案例 01：渠道按分传数据、本地按元比较——契约失真如何骗过测试

> 一条命令复现：`python3 demo.py`（Python 3.8+ 标准库，零第三方依赖）
> 证据分级：历史证据与合成演示的分级区分见 [EVIDENCE.md](EVIDENCE.md)

## 这是什么

一次真实支付链路事故的机制级重建：第三方渠道金额按「分」传递、本方系统按「元」记账，响应侧校验把两种单位的数值直接比较——平价场景下比较恒不等，**历史记录中受影响范围为当时全部下单请求（全量误拒）**。而当时的测试套件全绿。

案例价值不在「单位换算」这个知识点，而在回答三个更贵的问题：

1. 为什么测试存在且全绿，却没挡住事故？（**mock 同源假绿**：mock 与实现犯了同一个单位假设）
2. 修复后怎么证明不再犯？（**输入忠实于外部契约**的测试才有牙齿）
3. 体系从这次事故里沉淀了什么？（trap 命名进设计约束 + 同族问题排查 + 失败案例资产化）

## 五段结构

### 1. 原问题是什么，为什么普通检查没挡住

用户真机下单，提交订单被价格变更校验（price_changed）全量拒绝。检查链路当时是存在的：请求侧单位转换正确、校验逻辑在执行、测试套件全绿。失效机制不是「缺检查」，而是**检查的输入失真**——mock 数据按「元」构造，与被测实现共享同一个单位假设；测试证明的是「实现与 mock 一致」，不是「实现与外部契约一致」。

### 2. 人工和 Agent 分别做什么

按可审计证据（commit 元数据）表述，不做过程还原：

- 用户真机反馈与修复提交相隔 22 分钟
- 修复提交由本人在 Gitee 私有仓库完成，提交中声明了 Claude 共同参与（`Co-Authored-By: Claude`）
- 该提交同时记录了：金额归一化函数（centsToYuan）新增、响应侧两处比较修复、4 个测试文件 mock 改分对齐契约、新增 Formatter 单测、失败案例条目（evals）当场固化
- 当时的具体协作过程已无法还原，不能仅凭提交记录确定人工与 Agent 各自完成的步骤

### 3. 加了什么约束或检查

- **归一化显式化**：分→元换算收敛为单一 Formatter 入口，边界值（非整数分）单测覆盖
- **mock 契约对齐**：测试 mock 全部改为按分构造，与真实契约一致
- **trap 命名与约束引用**：防同源假绿约束在事故前 3 天已书面化（见 EVIDENCE.md A3——即约束已存在仍未拦住本次事故）；事故后教训被正式命名为 `api-field-contract-mock-false-green`，该约束在后续设计中持续被引用
- **同族排查**：事故当天另有 4 个「真机契约校准」修复（响应键位、幂等键、轮询契约）——mock 假绿是一族问题而非孤立 bug

### 4. 用什么输入复现，什么结果算通过

见 `demo.py` 四幕输出：

| 层 | 输入 | 事故版 | 修复版 |
|----|------|--------|--------|
| 校验层 | 渠道 60（分）vs 本地 0.60（元） | 误拒（全量拒绝） | 放行 |
| 测试·元值 mock | mock 按「元」构造 | **3/3 绿（假绿）** | — |
| 测试·忠实 fixture | fixture 按「分」构造 | 1/3（唯一「过」是碰巧） | 3/3 |

通过标准：忠实 fixture 组对修复版 3/3 绿，且平价放行/变价拒绝/漂移转探查三类用例各自成立。

### 5. 哪些情况仍然挡不住，哪些效果没有测量

- **资产化不是免疫针**：「防同源假绿」约束在本事故前 3 天已写入设计文档，事故当天仍发生同族问题——约束的书面化不等于约束的执行，执行靠的是 mock 契约对齐这类硬做法
- **否定性用例的局限**：变价拒绝用例对事故版「通过」——它对的理由是「恰好两个数不等」，否定性测试无法区分「对的理由」
- **未测量项**：同族契约失真在其它渠道的发生率、mock 契约对齐做法对同类事故的拦截率，均无统计——本案例不宣称普遍有效性
- **重构边界**：本重建是机制级简化（比较函数级），不还原完整下单链路；链路级回归依赖原私有仓库的测试套件，不在公开范围
